# MDMX512 Control Plane — experimental concept\n\n> Status: EXPERIMENTAL. This does not modify or replace the frozen FRAMESET_V1 host-to-RP2040 contract.\n\n## Hypothesis\n\nReserve one DMX/Art-Net/sACN universe from a lighting console as a **control plane**. Its 512 slots do not directly correspond to 512 physical output slots. Instead, they describe a compact set of operations over a rig already known by MDMX.\n\nA lighting console can already control complex external systems through fixture personalities. Media servers are the obvious precedent: a relatively small set of DMX parameters selects media, transforms layers, sets playback speed, opacity, position, etc., while the server performs the expensive work internally.\n\nMDMX512 applies that pattern to fixture expansion.\n\n```\nAvolites / other console\n        |\n        | one dedicated 512-slot control universe\n        v\n+------------------------------+\n| MDMX512 decoder              |\n| 16-byte header               |\n| 31 x 16-byte operator lanes  |\n+------------------------------+\n        |\n        +------ Rig Registry (MVR/GDTF/manual)\n        |       fixture IDs\n        |       groups/order\n        |       personalities\n        |       patch/universe/address\n        |\n        v\n+------------------------------+\n| Expansion Engine             |\n| SET / RAMP / WAVE / ...      |\n+------------------------------+\n        |\n        v\nUniverse 1 ... Universe N\n```\n\n## Why this can multiply output\n\nIt does **not** create arbitrary information. It exploits structure that MDMX already knows.\n\nExample: ten 51-channel fixtures occupy 510 physical slots. Their ten dimmers normally require ten independent output values. A single MDMX512 lane can instead describe:\n\n```\ntarget_group = 1\nattribute    = DIMMER\noperator     = RAMP\nstart        = 0%\nend          = 100%\n```\n\nThe receiver knows which ten fixtures belong to group 1 and computes ten independent dimmer outputs.\n\nThis is model-based expansion, not lossless compression of arbitrary DMX.\n\n## Hard information limit\n\nA 512-slot control plane cannot reproduce an arbitrary state of an unlimited number of independent output channels. If every output slot must be independently controllable at the same instant, the required input information grows with the output.\n\nThe useful case is when outputs share structure: same values, ramps, waves, phase/spread, chases, mirror/invert, spatial functions, stored presets, transforms derived from fixture order/geometry, or references to targets/scenes already stored in MDMX.\n\n## Protocol draft V0\n\nThe control universe is a **continuous declarative snapshot**, not a queue of commands. This is important because DMX is lossy and continuously repeated.\n\n### Global header: 16 slots\n\n| Offset | Size | Meaning |\n|---|---:|---|\n| 0–3 | 4 | ASCII MDMX |\n| 4 | 1 | protocol version = 1 |\n| 5 | 1 | profile = 1 |\n| 6 | 1 | global flags; bit 0 = armed |\n| 7 | 1 | bank |\n| 8–9 | 2 | global master, 16-bit coarse/fine |\n| 10–15 | 6 | reserved |\n\n### Operator lanes\n\n31 lanes x 16 slots = 496 slots.\n\n| Lane byte | Meaning |\n|---|---|\n| 0 | enabled |\n| 1 | opcode |\n| 2 | semantic attribute |\n| 3 | flags |\n| 4–5 | target group ID |\n| 6–7 | P0 |\n| 8–9 | P1 |\n| 10–11 | P2 |\n| 12–13 | P3 |\n| 14–15 | P4 |\n\nAll 16-bit values use DMX coarse/fine ordering.\n\nInitial opcodes: SET, RAMP, WAVE. The meaning of P0–P4 is opcode-specific, keeping every lane fixed-width while allowing the language to evolve.\n\n## Why declarative snapshots instead of commands\n\nBad model: channel changed -> execute command once. If a packet is dropped, the event can disappear; repeated packets can retrigger it.\n\nPreferred model: the complete universe describes what should be true now. Every frame can be evaluated atomically. Losing one frame delays the update; the next repeated frame repairs state naturally.\n\n## Recommended Avolites integration\n\nDo not begin by assuming one giant 512-channel personality is ergonomically ideal. Prototype the same protocol in modes MDMX64, MDMX128, MDMX256 and MDMX512. The logical protocol is identical; only the number of exposed lanes changes.\n\nA later Titan personality should expose semantic controls, not raw Channel 1...512. The console becomes the programmer/sequencer for MDMX parameters; MDMX remains responsible for expansion.\n\n## Critical distinction: Titan effects\n\nTitan's Shape Generator computes changing fixture attribute values for fixtures Titan knows individually. If the real fixtures are hidden behind one MDMX virtual fixture, Titan cannot send its internal per-real-fixture fan result.\n\nTherefore MDMX512 must expose effect parameters explicitly: target group, attribute, operator, base, size/span, speed, phase/spread, direction/order. Titan can cue/fade/chase those parameters, while MDMX computes the per-fixture result.\n\n## Configuration plane\n\nThe control universe should not carry the entire rig database. MDMX needs a persistent registry loaded by MVR/GDTF/manual configuration containing physical fixture identities, personalities, patch/universe/address, groups, ordering and optional geometry/calibration.\n\nThis stored model is where most of the apparent multiplication comes from.\n\n## Transport recommendation\n\nFor the first prototype, receive the MDMX512 control universe over Art-Net or sACN on a computer/Raspberry Pi. This avoids adding a physical DMX input stage before the semantics are proven. Later, the same 512-slot representation can be accepted from physical DMX.\n\n## Prototype proof\n\nprototype/mdmx512/protocol.py implements exact 512-byte encode/decode, 31 fixed operator lanes, SET/RAMP/WAVE, fixture/group registry and expansion into arbitrary universe buffers.\n\nprototype/mdmx512/test_protocol.py tests the minimal target case: 10 fixtures x 51 channels = 510 physical slots. One RAMP lane expands to ten independent dimmer slots:\n\n```\n0, 28, 57, 85, 113, 142, 170, 198, 227, 255\n```\n\nThis is the first proof of the control-plane idea. It is not yet a final protocol.\n
